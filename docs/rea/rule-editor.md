# rea / rule-editor

How `REA_UI` turns a served schema into a form and the form into a saved rule. Cited at `REA_UI@411c809` (branch `debug-ui`) unless stated.

## Schema → form
- The editor renders `GET /api/v1/RuleSchema` and adds what the schema does not carry through a per-code **UI map**: `mainSettingUIMap[<code>]` in `src/utils/rule/ruleUIConfig.ts` — `layout`, `inputs` type overrides, `linkedOptions`, `subGroups`, `inputWidths`, `referenceInputs`. `applyUIMapToBlock` (`src/utils/rule/ruleSchemaUtils.js:90-170`) moves the fields named in `subGroups` out of the top level into `blocks[{groupId, inputs}]` (a field may sit in several groups and stays one value) and stamps `linkedGroupId` on the options named in `linkedOptions`; `MainSetting.vue` shows a group's inputs as a dynamic row under its select while that option is selected (`layoutRows` inserts one row per linked select at `rowId + 0.5`, so two selects in one block resolve independently).
- **The 檢核範圍 欄位 menu is the served code's `conditions`, nothing more.** `getMainSettingByCode` picks the code out of the loaded schema (`src/stores/ruleEditor.js:263-269`); `RuleEditorDialog.vue:623` hands its `conditions` to `buildScopeFieldConfig` (`ruleSchemaUtils.js:284-298`), and `ScopeSetting.vue:1004-1018` lists them in the select (`:243-254`). The ui adds no item and reads none from another endpoint; where the thirteen live in the kernel: rea-kernel › Where the 檢核範圍 menu comes from. Cited at `REA_UI@5721638` (`develop`).
- UI-map keys are field identifiers, not names of their own (Field names).
- **A `dropdown` or a `radio` opens a linked row** — `LINKED_ROW_INPUT_TYPES` in `buildLinkedInputIdsMap` (`REA_UI@f959c2a src/views/rules/MainSetting.vue:647-651`, since `514f817`, 2026-10-20); before it only a dropdown did, so a radio with `linkedGroupId` options showed no sub-group. `collectMainPayloadFields` (`ruleSchemaUtils.js:235-242`) and the read view (`RuleShows.vue:326`, `:391`) treated both alike all along. First use: 202's `employmentType` radio, whose `FullTime` option links `fullTimeCheck` holding `fullTimeDoctorTypes` as `sortOptions` (`ruleUIConfig.ts:107-118`), the kernel's `VisibleWhen` on that field (`REA_kernel@480e69e _202.cs:47`) expressed in the map; the sub-group's label and options are served (plan ui-202-employment-type).
- A `String` field with `Options` renders as a text input unless the map says `dropdown` / `radio` (`getSchemaFieldType`, `ruleSchemaUtils.js:47-53`); `StringArray` infers `multiSelect`, `ObjectArray` `groupAdd`.
- **Sub-group overrides.** `subGroups.inputs[id]` is either a type string (type only) or an object — `SubGroupInput`: `type`, `label`, `prefixText`, `suffixText`, `placeholder`, `width` (`ruleUIConfig.ts`) — that `applyUIMapToBlock` merges over the served field (`ruleSchemaUtils.js:157-162`). One served field can therefore read as a different sentence in each mode, and a served label can be hidden with `label: ''`; the kernel's labels are untouched (`REA_kernel@2ff26b0 Codes/V1.0/_303.cs:33-36`, `_305.cs:39-40`).
- `MainSetting.vue` prints `label` above the control and `prefixText` / `suffixText` inline for every input type; the `textAdd` branch prints no label (`:254-291`). The read view (`RuleShows.vue:659`) joins prefix, value, suffix only.

## Field names
- **One rule, both directions.** A field's identifier is the kernel's `Value`; the ui's is that string with the first ASCII letter flipped and nothing else — there is no per-field renaming anywhere, in any code. Two layers do it, each reversible (`ucFirst(lcFirst(x)) === x`): the axios interceptor deep-transforms every key on `/api/v1/(RuleSchema|RuleSet|Options)` (`src/api/caseTransform.js:16-36`, `src/api/interceptors.js:14-33`), then `normalizeFieldIds` lowers the identifier *values* — a field's `value`, `optionsApi` tokens, `constraints[].type` — recursing into `subFields` and `fields` (`src/api/modules/rules/index.ts:72-95`). A saved `Main` key is therefore the kernel's PascalCase again. `options[].value` is data and passes untouched both ways (`01`, `ApplyDate`, `In`); only `condition.field` follows the identifiers (`FIELD_VALUE_KEYS = ['field']`).
- Kernel source and the live schema of 2026-09-11 carry the same Main and Reference names for all twenty codes, with one exception at `REA_kernel@458e663`: `_201.cs` has dropped its whole `ReferenceFields` block, which the 2026-09-11 deployment still served (`sources/2026-09-11-ruleschema-live.json.md@548ac767c5d8`) and the 2026-09-17 one no longer does (`sources/2026-09-17-ruleschema-live.json.md@ecc4c965567f` L6404-L7425). The coded name is otherwise the served name.
- **Group ids are the prototype's, not the kernel's.** The kernel has no sub-group concept; every `subGroups` key is a `REA_PROTO@3fdf47c tests/mock/api/rulesSpecificSetting.json` sub-blockId — 304 and 305 one-for-one, 303 minus the `Block` suffix, 306's `code` / `prefix` / `range` given a `diagnosis` prefix. The prototype names the *fields* a third way (the kernel's `BodyPartPrefixLen` is its `bodyPartPrefixRange`, 306's `DiagnosisCategory` its bare `category`, 307's `DiagnosisScope` its `filterFields`), so a prototype id is never evidence for a ui or a kernel id.
- **A key naming no served field is inert, not an error.** The map is looked up *by* the served field id and unmatched sub-group inputs are dropped (`ruleSchemaUtils.js:111`, `:155`), for `scopeSettingUIMap` too (`:190`); the cost is an input that never renders, with no warning. Seven such keys stand at `3ad7356` — 105 `mainSetting` for `Note` (rule-codes), 201 `referenceDates`, 307 `prefixLength` + `monthUnit` and the scope conditions' `prefixLen` / `prefixRange` (plan ui-map-orphans); 205/206's `doctorRole` + `employmentType` went with `3ad7356` (verified 2026-10-19), whose test pins 205/206 to `specialistCodes` alone.

## Disabled conditions
- **The kernel flags a condition, not a field.** `ConditionDescriptor.Disabled` — "顯示於 UI 但不可選，用於尚未實作 Translator 的條件" — was set only by 201, on nine of thirteen conditions, while the 1.1 translator handled four; since `REA_kernel@667734c` (2026-10-13) it handles twelve and every code flags one, `Robotic` (rea-kernel › The schema, scope-conditions › 7). Options are flagged too, and only the sortable inputs grey them — the scope dropdowns do not (plan ui-scope-option-flags). The prototype's `disabled` is a different thing: it locks an input inside a condition; no carrier for it is planned — the owner dropped that plan on 2026-10-19, its one concrete case (205/206 專任) having no field left to lock.
- **How the ui honours it.** The interceptor delivers it as `disabled`; `normalizeFieldIds` and `normalizeSchemaConditionDescriptor` keep it by spreading (`src/api/modules/rules/index.ts:72-95`, `:122`; `src/utils/rule/ruleSchemaUtils.js:177-191`), and the two maps that pick keys by name carry it explicitly — `buildScopeFieldConfig` (`ruleSchemaUtils.js:297`, fed the raw `conditions` by `RuleEditorDialog.vue:623`, `:353-355`) and `fieldOptions` (`src/views/rules/ScopeSetting.vue:1014`). The 欄位 option is disabled (`:252`, `:478`); 加入 and the empty state count only `selectableFieldOptions` (`:36-83`, `:1028`, `:1392`). A stored disabled condition still renders with its values: its 欄位 item carries `error` 「此條件尚未開放，請移除或改選其他條件」 from the moment it shows (`:236`, `:462`, `:1027-1030`), and a `field` rule fails the form (`:1563`), so `handleSave`'s scope validation stops before the request. Mock mode still flags 201's nine and no one else's `Robotic` (`mock/rulesData.js:5-8`, `:1038`) — the 2026-09-17 deployment's shape, stale since `667734c` (plan ui-scope-option-flags). Before `REA_UI@392230e` both maps dropped the flag and all thirteen were selectable. Cited at `392230e` (`debug-ui`).
- The add-on board takes its condition list from the first code, 101 (`src/views/addOn/AddOnBoard.vue:870-874`) — "the dictionary is shared by all codes". In the 2026-09-17 deployment that held except for 201's flags and one extra `VisibleWhen` on 101's `CaseTypeOptions`; at `REA_kernel@1706cb5` the flags are the same in every code and the `VisibleWhen` is the only difference left.

## RuleSet → editor
- What the ui reads of a `RuleSet` row — five top-level fields and the leaf `Name` never, the leaf `UpdatedAt` for single-group codes only — the `$select` refusal, and the store's quirks (`Main.GroupName` echoed, `OtherNote` outliving `Logic`) live in ruleset-api.
- **A stored option value is carried verbatim, never reconciled with today's schema.** 參考日期's options and `Default` come only from the served field — `src` has no date value literal (`REA_UI@a024004`, a grep of `ApplyDate`/`FuncDate` hits only `tests/`) — but an edited rule's `Reference.params` become the form's values as stored (`src/utils/rule/ruleNodeUtils.js:481-507`, `src/views/rules/ReferenceSetting.vue:272-289`) and go back out through `:162-189`; the served `Default` fills only an absent value. The kernel checks every `Params` value against the field's `Options` (`REA_kernel@e5ba92e src/API/NHI.API.ClaimValidator/Validation/FieldRuleValidator.cs:187-205`, 「不允許的選項」). So when an option's value is renamed, a rule saved before it fails on its next save: `db59964` (2026-09-18) renamed 203's 就醫日期 `ApplyDate` → `FuncDate` and put `ExecutionStartDate` first in `Default` (`Codes/V1.0/_203.cs:29`, `:38`); the sixteen other codes with 參考日期 keep `ApplyDate` (the commit message says fourteen), and 檢核範圍 年齡's own 基準日 uses `01` (`_203.cs:455`).
- **`Reference` changed shape in the kernel on 2026-09-29; the ui speaks it since `REA_UI@82908a2`** (2026-09-30, unpushed) — the dictionary, its order rule, and what `a024004` did with it: ruleset-api › `Reference`.

## Form → `Main`
- `handleSave` (`RuleEditorDialog.vue`) gives `buildRuleNodeFromEditorState` a function `module => collectMainPayloadFields(normalizedBlock, module.mainConfig)` (`ruleSchemaUtils.js`): the top-level `inputs` plus the `inputs` of every sub-group whose `groupId` is the `linkedGroupId` of a currently selected option, deduplicated by `value`; `buildMainPayloadBySchema` (`ruleNodeUtils.js`) keeps exactly those keys (`null` when unset). A hidden mode's leftover value is not sent — and `MainSetting.vue` does not clear it. Before `REA_UI@f69d5d9` the whitelist was the top-level `inputs` alone, so a saved 303/304/305 lost every sub-row value; a rule saved before that commit holds an empty sub-row set in the kernel until re-saved. Only `handleSave` was traced.
- Kernel side: a missing or `null` key fails only a `Required` field; an undeclared key is rejected (`REA_kernel@2ff26b0` `FieldRuleValidator.cs:78-95`, `SchemaExistenceValidator.cs:76-82`, `RuleSetSchemaValidationTests.cs:190-212`).

## The leaf envelope
- One rule module becomes one `Or` tree of leaves, one leaf per group (`buildRuleNodeFromEditorState` / `mergeNodesWithOr`, `src/utils/rule/ruleNodeUtils.js:231-241`, `:215-228`). The group the user named rides in `groupName` (`moduleToLeafNode`, `:205-212`); `buildRuleSetPayload` then stamps every leaf with `name` = the **rule code's display name** from `rules[].name`, and `updatedAt` (`addLeafMeta`, `:288-303`). On load `decomposeRuleNodeToEditorState` reads `leaf.groupName` (`:539-546`), and the dialog's `groupNames` array (`src/views/rules/RuleEditorDialog.vue:538`, `:569-576`) is not set by `loadFromRuleSet` (`src/stores/ruleEditor.js:83-106`), so after a reload names fall back to `群組N`. Keys are PascalCased at the axios boundary (`deepPascalizeKeys` / `deepCamelizeKeys`, `src/api/caseTransform.js`), so the wire carries `Name` and `GroupName`. Cited at `REA_UI@411c809` (`debug-ui`).
- **The kernel carries `GroupName` since `a63ad16` (2026-09-18) — the 2026-09-17 ruling is delivered.** `RuleNode.GroupName` (`REA_kernel@6540a4c POCO/V1/Rules/RuleSet.cs:115-118`); `StructureValidator` requires a leaf's `Name` *and* `GroupName` non-blank and `GroupName` unique among one `Code`'s leaves — `Name` is display only, no longer unique (`Validation/StructureValidator.cs:29-36`, `:72-76`; `6633198`). The translator names engine rules `Rule_<code>_<GroupName>` (`Translator/V1.1/RuleSetTranslator.cs:65-71`). The ui's leaf — `groupName` from the module, `name` the code's display name — satisfies both as it stands, so the ui needs no change, as the owner ruled on 2026-09-17; a second group of one code no longer 400s. The unpushed `debug-api_groupName-to-Name` build (rea-ui › Branches) is moot. Before `a63ad16` the kernel read `Name` as the group name and discarded `GroupName` in silence (`458e663`). One gap the form leaves to the kernel: 群組名稱 is `required` and defaults to `群組N` (`src/views/rules/RuleEditorDialog.vue:301-303`, `:343-349`) but is never checked for uniqueness, so two groups typed with the same name pass the dialog and come back as the kernel's 400「重複的 GroupName」— a nicety, not a defect the owner has asked to fix.
