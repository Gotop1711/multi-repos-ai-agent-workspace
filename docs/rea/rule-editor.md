# rea / rule-editor

How `REA_UI` turns a served schema into a form and the form into a saved rule. Cited at `REA_UI@411c809` (branch `debug-ui`) unless stated.

## Schema → form
- The editor renders `GET /api/v1/RuleSchema` and adds what the schema does not carry through a per-code **UI map**: `mainSettingUIMap[<code>]` in `src/utils/rule/ruleUIConfig.ts` — `layout`, `inputs` type overrides, `linkedOptions`, `subGroups`, `inputWidths`, `referenceInputs`. `applyUIMapToBlock` (`src/utils/rule/ruleSchemaUtils.js:90-170`) moves the fields named in `subGroups` out of the top level into `blocks[{groupId, inputs}]` (a field may sit in several groups and stays one value) and stamps `linkedGroupId` on the options named in `linkedOptions`; `MainSetting.vue` shows a group's inputs as a dynamic row under its select while that option is selected (`layoutRows` inserts one row per linked select at `rowId + 0.5`, so two selects in one block resolve independently).
- UI-map keys are field identifiers, not names of their own (Field names).
- A `String` field with `Options` renders as a text input unless the map says `dropdown` / `radio` (`getSchemaFieldType`, `ruleSchemaUtils.js:47-53`); `StringArray` infers `multiSelect`, `ObjectArray` `groupAdd`.
- **Sub-group overrides.** `subGroups.inputs[id]` is either a type string (type only) or an object — `SubGroupInput`: `type`, `label`, `prefixText`, `suffixText`, `placeholder`, `width` (`ruleUIConfig.ts`) — that `applyUIMapToBlock` merges over the served field (`ruleSchemaUtils.js:157-162`). One served field can therefore read as a different sentence in each mode, and a served label can be hidden with `label: ''`; the kernel's labels are untouched (`REA_kernel@2ff26b0 Codes/V1.0/_303.cs:33-36`, `_305.cs:39-40`).
- `MainSetting.vue` prints `label` above the control and `prefixText` / `suffixText` inline for every input type; the `textAdd` branch prints no label (`:254-291`). The read view (`RuleShows.vue:659`) joins prefix, value, suffix only.

## Field names
- **One rule, both directions.** A field's identifier is the kernel's `Value`; the ui's is that string with the first ASCII letter flipped and nothing else — there is no per-field renaming anywhere, in any code. Two layers do it, each reversible (`ucFirst(lcFirst(x)) === x`): the axios interceptor deep-transforms every key on `/api/v1/(RuleSchema|RuleSet|Options)` (`src/api/caseTransform.js:16-36`, `src/api/interceptors.js:14-33`), then `normalizeFieldIds` lowers the identifier *values* — a field's `value`, `optionsApi` tokens, `constraints[].type` — recursing into `subFields` and `fields` (`src/api/modules/rules/index.ts:72-95`). A saved `Main` key is therefore the kernel's PascalCase again. `options[].value` is data and passes untouched both ways (`01`, `ApplyDate`, `In`); only `condition.field` follows the identifiers (`FIELD_VALUE_KEYS = ['field']`).
- Kernel source and the live schema of 2026-09-11 carry the same Main and Reference names for all twenty codes, with one exception at `REA_kernel@458e663`: `_201.cs` has dropped its whole `ReferenceFields` block, which the 2026-09-11 deployment still served (`sources/2026-09-11-ruleschema-live.json.md@548ac767c5d8`) and the 2026-09-17 one no longer does (`sources/2026-09-17-ruleschema-live.json.md@ecc4c965567f` L6404-L7425). The coded name is otherwise the served name.
- **Group ids are the prototype's, not the kernel's.** The kernel has no sub-group concept; every `subGroups` key is a `REA_PROTO@3fdf47c tests/mock/api/rulesSpecificSetting.json` sub-blockId — 304 and 305 one-for-one, 303 minus the `Block` suffix, 306's `code` / `prefix` / `range` given a `diagnosis` prefix. The prototype names the *fields* a third way (the kernel's `BodyPartPrefixLen` is its `bodyPartPrefixRange`, 306's `DiagnosisCategory` its bare `category`, 307's `DiagnosisScope` its `filterFields`), so a prototype id is never evidence for a ui or a kernel id.
- **A key naming no served field is inert, not an error.** The map is looked up *by* the served field id and unmatched sub-group inputs are dropped (`ruleSchemaUtils.js:111`, `:155`), for `scopeSettingUIMap` too (`:190`); the cost is an input that never renders, with no warning. Nine such keys stand at `458e663` — 105 `mainSetting` for `Note` (rule-codes), 205/206 `doctorRole` + `employmentType` (plans 205-main-fields, field-locking), and 201 `referenceDates`, 307 `prefixLength` + `monthUnit` and the scope conditions' `prefixLen` / `prefixRange` (plan ui-map-orphans).

## Disabled conditions
- **The kernel flags a condition, not a field.** `ConditionDescriptor.Disabled` — "顯示於 UI 但不可選，用於尚未實作 Translator 的條件" — is set only by 201, on nine of thirteen conditions; the four left enabled are the translator's four, and saving any other one 500s (rea-kernel › Save translates). The prototype's `disabled` is a different thing: it locks an input inside a condition (plan field-locking).
- **The ui loses it on the way to the select.** The interceptor delivers it as `disabled`, and `normalizeFieldIds` and `normalizeSchemaConditionDescriptor` keep it by spreading (`src/api/modules/rules/index.ts:72-95`, `:122`; `src/utils/rule/ruleSchemaUtils.js:177-191`). Then two maps pick keys by name and drop it: `buildScopeFieldConfig` (`ruleSchemaUtils.js:284-298`, fed the raw `conditions` by `RuleEditorDialog.vue:623`, `:353-355`) and `fieldOptions` (`src/views/rules/ScopeSetting.vue:1000-1014`). Both 欄位 selects render every option enabled (`:246-251`, `:470-475`), and "can anything be added" counts all of them (`:36-83`, `:1381`). Cited at `REA_UI@411c809` (`debug-ui`). Plan disabled-conditions.
- The add-on board takes its condition list from the first code, 101 (`src/views/addOn/AddOnBoard.vue:870-874`) — "the dictionary is shared by all codes". In the 2026-09-17 deployment that holds except for 201's flags and one extra `VisibleWhen` on 101's `CaseTypeOptions`.

## Form → `Main`
- `handleSave` (`RuleEditorDialog.vue`) gives `buildRuleNodeFromEditorState` a function `module => collectMainPayloadFields(normalizedBlock, module.mainConfig)` (`ruleSchemaUtils.js`): the top-level `inputs` plus the `inputs` of every sub-group whose `groupId` is the `linkedGroupId` of a currently selected option, deduplicated by `value`; `buildMainPayloadBySchema` (`ruleNodeUtils.js`) keeps exactly those keys (`null` when unset). A hidden mode's leftover value is not sent — and `MainSetting.vue` does not clear it. Before `REA_UI@f69d5d9` the whitelist was the top-level `inputs` alone, so a saved 303/304/305 lost every sub-row value; a rule saved before that commit holds an empty sub-row set in the kernel until re-saved. Only `handleSave` was traced.
- Kernel side: a missing or `null` key fails only a `Required` field; an undeclared key is rejected (`REA_kernel@2ff26b0` `FieldRuleValidator.cs:78-95`, `RuleSetSchemaValidationTests.cs:190-212`).

## The leaf envelope
- One rule module becomes one `Or` tree of leaves, one leaf per group (`buildRuleNodeFromEditorState` / `mergeNodesWithOr`, `src/utils/rule/ruleNodeUtils.js:231-241`, `:215-228`). The group the user named rides in `groupName` (`moduleToLeafNode`, `:205-212`); `buildRuleSetPayload` then stamps every leaf with `name` = the **rule code's display name** from `rules[].name`, and `updatedAt` (`addLeafMeta`, `:288-303`). On load `decomposeRuleNodeToEditorState` reads `leaf.groupName` (`:539-546`), and the dialog's `groupNames` array (`src/views/rules/RuleEditorDialog.vue:538`, `:569-576`) is not set by `loadFromRuleSet` (`src/stores/ruleEditor.js:83-106`), so after a reload names fall back to `群組N`. Keys are PascalCased at the axios boundary (`deepPascalizeKeys` / `deepCamelizeKeys`, `src/api/caseTransform.js`), so the wire carries `Name` and `GroupName`. Cited at `REA_UI@411c809` (`debug-ui`).
- **The kernel's source reads `Name` as the group name.** `RuleNode` has no `GroupName` (`REA_kernel@876cd3d POCO/V1/Rules/RuleSet.cs:69-117`); `StructureValidator` requires `Name` non-blank and unique among one `Code`'s leaves (`Validation/StructureValidator.cs:29-35`, `:70-73`), on `develop` since `f49ea00` and unchanged at `458e663` (rea-kernel); a `GroupName` key is discarded in silence (`API/NHI.API.ClaimValidator/Program.cs:9-12`). Against that rule one group saves and two 400 as duplicates.
- **Decided: the ui keeps `GroupName`; the kernel will carry it.** The owner, 2026-09-17: `GroupName` is to be implemented in the kernel, and the ui needs no change for it. It is **not yet in the kernel's source** — remote `develop` had no new commit past `458e663` on 2026-09-17 (a dry-run fetch) — so until it lands, a build from `develop` rejects a second group.
